## 1. Resumen ejecutivo

La auditoría encontró **20 defectos únicos** después de deduplicar los hallazgos compartidos entre
los distintos barridos:

- **3 CRITICAL**: todos confirmados por tres revisores adversariales independientes.
- **15 WARNING**: defectos reales con impacto condicionado, degradación operacional o riesgo de regresión.
- **2 SUGGESTION/INFO**: limitaciones de producto o calidad que no constituyen una regresión inmediata.

Los tres riesgos principales son:

1. La protección SSRF valida DNS antes de hacer las solicitudes, pero no fija la conexión a la IP
   validada. Un hostname controlado puede realizar DNS rebinding y dirigir solicitudes autenticadas
   hacia servicios internos.
2. GitHub Action usa un único `/tmp/ghagga-memory.db` para todos los repositorios y ejecuciones.
   En runners persistentes puede reutilizar memoria de otro repositorio o corromperse por concurrencia.
3. La pantalla Settings ignora errores al cargar configuración, muestra valores locales por defecto y
   permite guardarlos sobre una configuración que nunca fue cargada correctamente.

La base automatizada es amplia: **6.057 tests pasan**, los **8 proyectos TypeScript** pasan typecheck y
`pnpm audit --prod` no encontró vulnerabilidades conocidas. Sin embargo, los problemas prioritarios están
principalmente en bordes de integración, fallos parciales, aislamiento entre ejecuciones y contratos de
despliegue que los tests actuales no modelan.

## 3. Hallazgos CRITICAL

### SEC-001 — DNS rebinding elude la protección SSRF

**Ubicación**

- `apps/server/src/lib/safe-url.ts:223-248`
- `apps/server/src/queues/review.ts:102-129,145-178,746-811`
- `packages/core/src/providers/gateway-discovery.ts:43-68`
- `packages/core/src/providers/gateway.ts:54-96`

**Descripción**

`validateOutboundUrl()` resuelve el hostname con `dns.lookup(..., { all: true })`, valida las IPs y
devuelve la URL original. La IP validada no forma parte del resultado y no se instala un dispatcher,
lookup personalizado o socket fijado. Los `fetch()` de discovery y generación resuelven nuevamente el
hostname al abrir cada conexión.

`redirect: 'manual'` evita redirecciones hacia una IP privada, pero no evita DNS rebinding. Un hostname
controlado puede responder con una IP pública durante la validación y con loopback, metadata cloud o una
IP RFC1918 durante el `fetch()` posterior.

**Impacto**

- SSRF hacia servicios internos accesibles desde el worker.
- El discovery envía `Authorization: Bearer <gatewayToken>`.
- La generación envía el token, system prompt y contenido derivado del repositorio.
- Puede convertirse en exposición de secretos/código o interacción con paneles internos.

**Prerequisitos**

El atacante necesita controlar el hostname configurado como gateway o influir sobre su DNS. Esto reduce
la explotabilidad general, pero no elimina el defecto: el objetivo incremental del atacante no es recibir
los datos como gateway legítimo, sino redirigirlos hacia otro servicio interno.

**Remediación recomendada**

1. Resolver una sola vez y validar todas las respuestas A/AAAA.
2. Elegir una IP aprobada y fijar la conexión HTTP a esa IP mediante un dispatcher/agent con lookup
   controlado, preservando `Host` y SNI.
3. Revalidar cada conexión nueva y cada redirect si en el futuro se habilitan redirects.
4. Rechazar respuestas DNS mixtas que incluyan rangos públicos y privados.
5. Aplicar allowlists de protocolos y, cuando sea posible, de puertos.

**Tests de cierre**

- DNS responde pública durante validación y privada durante conexión: la conexión debe bloquearse.
- Respuestas mixtas pública/privada: rechazo completo.
- IPv4-mapped IPv6, loopback, link-local y metadata cloud.
- Discovery y generate deben compartir la misma política/pinning.

**Verificación adversarial:** `stands` en 3/3 revisiones.

### ACTION-MEM-001 — Base SQLite global compartida entre repositorios y jobs

**Ubicación**

- `apps/action/src/index.ts:214-241,317-335`
- `apps/action/src/index.test.ts:409-466`

**Descripción**

La Action utiliza siempre `/tmp/ghagga-memory.db`. La clave del cache remoto sí incluye el repositorio,
pero la ruta física local no. En un cache miss solamente se registra “fresh database”; no se elimina ni
reemplaza un archivo que haya quedado de una ejecución anterior.

En GitHub-hosted runners el filesystem efímero reduce el riesgo, pero los self-hosted runners persistentes
están documentados y pueden ejecutar secuencial o concurrentemente múltiples repositorios. Dos procesos
también pueden abrir, exportar y cachear el mismo archivo.

**Impacto**

- Una ejecución con cache miss puede abrir memoria residual de otro repositorio.
- El snapshot puede guardarse después bajo la clave de cache del repositorio equivocado.
- Jobs concurrentes pueden sufrir locking, last-writer-wins o snapshots inconsistentes.
- Aunque las consultas tengan scoping lógico, el archivo físico contiene datos de más de un ámbito y
  rompe el límite esperado de aislamiento.

**Remediación recomendada**

1. Construir la ruta desde `RUNNER_TEMP`, repository ID/full name y run/job ID.
2. Crear un directorio privado por ejecución.
3. En cache miss, garantizar que el destino no existe.
4. Restaurar a un temporal y hacer rename atómico.
5. Cerrar SQLite antes de exportar/cachear y limpiar el directorio en `finally`.
6. Evitar que procesos concurrentes compartan el mismo destino incluso para el mismo repositorio.

**Tests de cierre**

- Repo A deja archivo; Repo B tiene cache miss: B debe iniciar vacío.
- Dos jobs simultáneos no deben usar la misma ruta.
- Restore fallido no debe abrir un archivo residual.
- El cache debe contener un snapshot cerrado y consistente.

**Verificación adversarial:** `stands` en 3/3 revisiones.

### PRODOPS-001 — Error de carga permite sobrescribir Settings

**Ubicación**

- `apps/dashboard/src/pages/Settings.tsx:27-29,43-116,157-200,255-260,733-734`
- `apps/dashboard/src/lib/api.ts:180-185`

**Descripción**

La página extrae únicamente `data` e `isLoading` de `useSettings`; ignora `isError` y `error`. El estado
local se inicializa con defaults y sólo se sincroniza cuando `settings` es truthy. Cuando el GET falla,
React Query termina con `data=undefined` e `isLoading=false`, por lo que desaparece el spinner y se muestra
un formulario editable con defaults. Al cambiar de repositorio también puede quedar el estado del repo
anterior.

El botón Save sólo se deshabilita durante la mutación. Nada exige que la configuración se haya cargado
correctamente antes de enviar el estado local.

**Impacto**

- Sobrescritura accidental de configuración existente con defaults.
- Copia involuntaria de valores de un repositorio a otro tras un fallo de carga.
- Cambio no intencional a `useGlobalSettings: true` o pérdida de ajustes específicos.

**Remediación recomendada**

1. Modelar explícitamente `loading`, `error`, `success` y `empty/not configured`.
2. No renderizar el formulario editable ante error.
3. Mostrar mensaje, retry y contexto del repositorio afectado.
4. Habilitar Save solamente después de una carga exitosa o una creación explícita confirmada.
5. Resetear el estado local inmediatamente al cambiar de repo.

**Tests de cierre**

- GET 500/401/timeout: se muestra error y Save está ausente o deshabilitado.
- Cambio A → B con error de B: ningún valor de A aparece como editable para B.
- Retry exitoso hidrata el formulario y recién entonces habilita Save.

**Verificación adversarial:** `stands` en 3/3 revisiones.

## 4. Hallazgos WARNING — seguridad y operación

### SEC-002 — OAuth `state` reutilizable y no ligado al navegador

**Ubicación:** `apps/server/src/routes/oauth.ts:39-81,157-181,184-253`.

El estado contiene timestamp y HMAC global, pero no un nonce de un solo uso ni asociación con cookie o
sesión. Es reutilizable durante cinco minutos. Además, `elapsed = now - ts` sólo rechaza valores mayores
al TTL; un timestamp futuro válidamente firmado permanece aceptable hasta ese instante más el TTL.

**Impacto:** login CSRF/account confusion; una víctima puede completar el callback iniciado para la cuenta
del atacante y terminar operando sobre el tenant equivocado.

**Remediación:** nonce CSPRNG de un solo uso, cookie `HttpOnly Secure SameSite=Lax`, consumo atómico,
validación `0 <= elapsed <= TTL` y `redirect_uri` consistente en el exchange.

---

### SEC-003 — `/health/detailed` público expone información y carga DB

**Ubicación:** `apps/server/src/index.ts:151-188`.

El endpoint detallado no está bajo `/api/*`, por lo que tampoco recibe el rate limiter correspondiente.
Cada request ejecuta una consulta y devuelve mensaje crudo del driver, uptime, RSS y estado del circuit
breaker.

**Impacto:** reconocimiento de infraestructura, filtrado de errores internos y amplificación de carga DB.

**Remediación:** restringir a red/autenticación de monitoreo, devolver estado agregado, cachear/rate-limit
y nunca exponer `error.message` del driver.

---

### SEC-004 / PRODOPS-003 — `REDIS_URL`, autenticación y TLS ignorados

**Ubicación**

- `docs/configuration.md:17-19`
- `apps/server/src/lib/redis.ts:14-19`
- `apps/server/src/queues/review.ts:184-189`
- `.env.example:28-36`

La documentación declara `REDIS_URL` como configuración preferida, pero tanto el singleton como el cliente
de BullMQ construyen la conexión sólo con host/port. No aplican username, password ni TLS. Compose levanta
Redis sin autenticación.

**Impacto:** despliegues con Redis administrado fallan o conectan al destino incorrecto; acceso lateral a
Redis permite leer/modificar jobs, callbacks y resultados.

**Remediación:** usar `REDIS_URL` como fuente principal en todos los clientes; soportar ACL, TLS y password;
validar al arrancar que las credenciales esperadas realmente se aplican; mantener Redis en una red privada.

---

### SEC-005 — Supply chain flotante y runtime como root

**Ubicación:** `apps/server/Dockerfile:14-16,51-78,121-132`.

La imagen usa tags flotantes, `pnpm@9`, descarga OpenCode sin checksum/firma e instala globalmente Gemini
CLI y Copilot sin versiones exactas. Algunos fallos se ocultan con `|| true`. No hay `USER` no-root.

**Impacto:** cambios o compromisos upstream entran de forma no reproducible; los CLIs reciben código y
credenciales con privilegios root dentro del contenedor.

**Remediación:** imágenes por digest, versiones exactas, SHA256/Sigstore, no ocultar fallos, SBOM/scan,
usuario no-root, filesystem/capabilities mínimos.

---

### SEC-006 — El worker Compose no recibe `STATE_SECRET`

**Ubicación**

- `docker-compose.yml:67-89`
- `apps/server/src/queues/review.ts:680-692`
- `apps/server/src/github/runner.ts:86-91`

Cada dispatch deriva un callback secret antes del bloque de dispatch. El worker documentado por Compose no
recibe `STATE_SECRET`, por lo que jobs con runner inline pueden fallar antes de ejecutar static analysis.

**Remediación:** inyectar el secreto, validarlo fail-fast en el entrypoint del worker y separar mediante
domain separation las claves usadas para OAuth y callbacks.

## 5. Hallazgos WARNING — core, Action y Forge

### ACTION-LIFE-002 — SQLite no se cierra ni persiste ante fallos posteriores

**Ubicación:** `apps/action/src/index.ts:251-335,349-352`.

El storage se cierra después de publicar el comentario. Si el pipeline, listado de comentarios o
create/update del comentario arrojan una excepción, el control salta al catch exterior y omite `close()` y
cache save. Si `close()` falla, el código igualmente puede intentar cachear un archivo stale.

**Impacto:** pérdida de observaciones del run, handles abiertos y snapshots inconsistentes.

**Remediación:** `finally` para cerrar, cachear únicamente después de cierre exitoso y desacoplar el
resultado del review de la publicación del comentario.

---

### CORE-INTEL-003 — Fallos de code-intel se reportan como éxito

**Ubicación**

- `packages/core/src/pipeline/gather-safe.ts:120-158`
- `packages/core/src/pipeline/gather-context.ts:156-165`
- `packages/core/src/pipeline/finalize.ts:56-57`

Las consultas por archivo se ejecutan con `Promise.allSettled`, pero los outcomes rejected se descartan.
Si todas fallan puede informarse `0/0 files`, no agregarse ningún `failedStep` y conservarse
`coverageComplete=true`.

**Impacto:** reviews aparentemente completas se generan sin el contexto estructural esperado; la
degradación queda invisible para usuario y observabilidad.

**Remediación:** contar éxitos/fallos, registrar degradación, marcar fallo cuando todas las consultas
fallan y reportar `filesQueried`, `filesFailed` y duración real.

### CORE-CONC-004 — `reviewConcurrency <= 0` produce loop infinito

**Ubicación**

- `packages/core/src/utils/concurrency.ts:35-50`
- `packages/core/src/pipeline/execute.ts:201-233`
- `packages/core/src/types.ts:241-244`
- `packages/core/src/agents/workflow.ts:169-173,242`
- `packages/core/src/agents/consensus.ts:241-245,289`

El loop avanza con `i += concurrency`. Con cero repite batches vacíos para siempre; con negativos retrocede.
`ReviewSettings.reviewConcurrency` llega desde la API pública sin validación central.

**Impacto:** job colgado, consumo indefinido de runner/worker y timeout tardío.

**Remediación:** validar entero finito `>= 1` en el boundary de settings y defensivamente dentro del helper;
validar también delays no negativos.

### FORGE-UPSERT-005 — Delete-before-create pierde el review anterior

**Ubicación**

- GitHub: `packages/forge/src/.../github-forge-adapter.ts:220-250`
- GitLab: `packages/forge/src/.../gitlab-forge-adapter.ts:178-207`

Los adaptadores eliminan todos los summaries existentes antes de publicar el reemplazo. Si delete funciona

**Impacto:** pérdida visible de información válida ante un fallo transitorio.

**Remediación:** actualizar el último comentario in-place usando el port ya disponible o crear primero y

## 7. Sugerencias e información

### MEM-HYBRID-006 — La búsqueda semántica es sólo reranking léxico

**Ubicación**

- SQLite: `packages/core/src/memory/sqlite.ts:363-431`
- PostgreSQL: `packages/db/src/queries.ts:758-782`

Ambos backends primero exigen candidatos obtenidos por FTS/MATCH y luego calculan embeddings/reranking. Si
no hay overlap léxico, retornan antes de usar la similitud semántica. Por ejemplo, una observación sobre
“credential exposure” no recuperará necesariamente una consulta “secret leakage” aunque los embeddings
sean cercanos.

**Clasificación:** limitación funcional y de naming, no regresión inmediata.

**Opciones:** unir candidatos ANN/vectoriales con candidatos keyword o documentar/renombrar la feature como
“semantic reranking”.

---

### PRODOPS-009 — Cobertura sin thresholds ni gate de PR

**Ubicación**

- `.github/workflows/ci.yml:108-149`
- `apps/dashboard/vitest.config.ts:17-28`
- `apps/server/vitest.config.ts:10-15`
- demás configuraciones Vitest de workspace

La cobertura se ejecuta después del merge a `main` y no existen thresholds. Una regresión grande no bloquea
PR, merge ni release.

**Recomendación:** mínimos por paquete, gate focalizado en PR y tendencia incremental para no convertir deuda
histórica en un bloqueo inmediato.

## 10. Definition of Done global

La remediación de esta auditoría debería considerarse cerrada cuando:

- cada finding tenga test de regresión o evidencia de verificación equivalente;
- DNS/HTTP se pruebe contra rebinding y respuestas mixtas;
- dos repositorios/jobs nunca compartan la misma ruta SQLite;
- ninguna pantalla permita guardar datos que no fueron cargados o creados explícitamente;
- Redis funcione con URL TLS/autenticada y falle rápido ante configuración inconsistente;
- API y worker tengan sondas de salud específicas;
- fallos parciales de code-intel aparezcan en metadata y observabilidad;
- los parámetros públicos se validen antes de llegar a helpers/DB;
- publicación de comentarios preserve el review anterior ante errores transitorios;
- typecheck, tests, lint, auditoría de dependencias y tests de integración queden verdes;
- se ejecute la revisión correspondiente antes de commit, push y PR conforme a las reglas del proyecto.
