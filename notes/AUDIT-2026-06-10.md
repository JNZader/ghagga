## Resumen ejecutivo

**2 CRITICAL, ~19 HIGH, ~31 MEDIUM, ~37 LOW.** Los temas dominantes:

1. **Features enteras que no funcionan** y nadie lo notó porque todo degrada "gracefully":
   el modo `diagnostic` es inalcanzable, la memoria del Action queda congelada tras el primer run,
   el hybrid search de SQLite está doblemente roto, el memory recall de Postgres devuelve ~nada,
   y el happy path `login → review` del CLI sale con exit 1.
2. **Authz inconsistente en el server**: el patrón `user.installationIds.includes(...)` está en todos
   los routers EXCEPTO `runner.ts` (cross-tenant write) + SSRF vía `gatewayUrl`.
3. **El degradado "graceful" esconde bugs**: catch-all que tragan errores reales (migración SQLite,
   embeddings, memoria) convierten fallas en silencio.
4. **Lo que está BIEN** (verificado y descartado): crypto AES-GCM sólida (IV random, auth tag verificado),
   HMAC webhook timing-safe y en orden correcto, SQL parametrizado en todos lados, dashboard sin XSS,
   confirmaciones destructivas bien hechas, 0 TODO/FIXME, solo 3 `as any` en producción.

## Temas sistémicos (lo que importa más que cualquier bug puntual)

1. **"Graceful degradation" sin observabilidad = bugs invisibles.** MEM-H2/H3, ACT-H1, DSH-A3: todos
   tragados por catch-all. Regla: degradar SÍ, pero loggeando la causa raíz y con métrica/test que
   detecte la feature muerta. Un test round-trip real (no mock) por backend hubiera atrapado 3 HIGH.
2. **Contratos sin enforcement**: topic_key "único" sin constraint, precedencia de config documentada
   pero no implementada, docs que prometen GITHUB_TOKEN fallback inexistente, comment "prefix" que
   reemplaza. Donde el contrato importa, ponerlo en el schema o en un test, no en un comentario.
3. **El borde LLM es frontera de confianza en AMBAS direcciones**: diff→prompt (injection) y
   output→comment/memoria (ALL-H2, MEM-M6). Sanitizar centralizado en format.ts + marco "untrusted"
   en memoria re-inyectada.
4. **Duplicación divergente**: 4 diff parsers, 2 esquemas de cache key, action/execution.ts copia
   de core/execution.ts sin el clearTimeout. Una sola fuente por concepto.

## Addendum — Codex GPT-5.5 (voz cross-engine, contrarian)

> Nota: el output de Codex llegó truncado (solo puntos 4-5 + estructurales). Lo que sobrevivió
> corrobora y GENERALIZA hallazgos de las voces Claude:

**CDX-1 (🟠, generaliza MEM-M6 + ALL-H2): el wrapping "untrusted" solo cubre el diff.**
La política existe y está bien aplicada al diff (`agents/prompts.ts:305-317`, usada en simple/workflow).
Pero entran al prompt como texto CONFIABLE: findings de static analysis (`prompts.ts:328-330` — vienen
del repo target / callback del runner), observaciones de memoria (`prompts.ts:333-335`), y outputs de
especialistas en la síntesis del workflow (`workflow.ts:247-299` — texto generado por modelo re-inyectado
sin política). Fix propuesto: prompt parts tipadas (`trustedInstruction` / `untrustedDiff` /
`untrustedToolOutput` / `untrustedMemory` / `modelOutputForSynthesis`) construidas por UN builder,
no concatenación de strings.

**CDX-2 (🟡, extiende ALL-H2): el escaping del comment es por-campo e incompleto.**
Solo `finding.message` escapa pipes/newlines (`format.ts:303-312`); `file`, `category`, `severity`,
label de source, model strings y `summary` van crudos. La mention al autor del PR se appendea cruda
desde el webhook (`format.ts:337-340` + `queues/review.ts:552-564`). Los findings de static analysis
pueden venir del callback payload del runner (`runner-callback.ts:76-82`) → otra fuente no confiable
que termina renderizada como Markdown bajo identidad del bot.

**CDX-3 (estructural): versionar el protocolo del workflow inyectado.** Hoy se confía en el
`workflowSha` cacheado; si el template evoluciona, hay skew silencioso entre lo que el server espera
y lo que el workflow viejo de un repo manda. Guardar hash/versión del template y reconciliar antes
del dispatch.

**CDX-4 (estructural, corrobora SRV-7): persistir el estado del dispatch.** Ligar `callbackId` a
reviewId/repo/pr/headSha/versión, enforcement de single-use, y validar el shape del payload antes
del write a Redis.

**CDX-5 (estructural): una librería de trust-boundary** que centralice: construcción de prompt parts,
escaping de Markdown, validación de schema de static-analysis, y labels de procedencia de contenido.
Reduce clases enteras de bugs en server + runner + core + dashboard de una.
